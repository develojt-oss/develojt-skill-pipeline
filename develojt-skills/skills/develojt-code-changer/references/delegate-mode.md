# Delegation Mode (delegate) — transitioning requirement additions/modifications/deletions into the SPEC via deriver procedures (classifications: addition / candidate adoption / change·deletion)

When operations (post-development) needs a new feature or an existing requirement must change, **the SPEC must change before the code** (R1 — the SPEC's change owner is the deriver). The lead never writes the SPEC directly. Instead it has **a subagent perform the deriver's transition procedure** to transition the SPEC, then carries the result into code with develojt-code-builder's five essentials.

The deriver skill carries `disable-model-invocation`, so other skills can't call it — which is why this is not a "skill invocation" but **"procedure reuse"**: the lead spawns a subagent, and that agent follows the deriver's procedure documents (references) to transition `spec/SPEC.md`.

| Classification | What | deriver procedure | SPEC result | STORYBOARD sync (only when present) |
|---|---|---|---|---|
| **Addition** (incl. the `--add` form) | Adding a new requirement | incremental mode (`incremental-mode.md`) | New IDs added | step 3-b: promote new-FR enrollment (`[No UI]`) |
| **Change/deletion** (incl. the `--change` form) | Modifying/deleting existing requirements | change mode (`change-mode.md`) | `[Removed]` + (on modification) new IDs, non-destructive transition | step 3-b: remap transition sync |
| **Conflict resolution** (the 'conflict-file input' section) | Applying the human verdicts (A/B) on design↔SPEC conflicts | A: change mode (`change-mode.md`) / B: none | A: `[Removed]`+new IDs / B: SPEC invariant | that section's remap stage (not 3-b) |

> Code-only fixes (bugs, quality, refactoring — **requirements invariant**) are not this mode → classification 'code-only' (`revise-mode.md`).

## Entry conditions

- `spec/SPEC.md` already exists (finalized).
- **This is the operations phase — `plan/PRD.md` and `spec/joblist.md` are not consulted** (their lifecycles ended with development). Both the source of truth and the impact scope are **the SPEC only**.
- Entered under intake classification **addition** or **change/deletion** (after the user confirmation of the develojt-code-changer intake gate).

## Core principles

- **SPEC only — the file, not context.** Never reference the PRD or joblist. When impact scope is needed, judge by the SPEC's **behavior chains** (the chains are in the SPEC). **Series** is checkable in the SPEC only when a deriver increment left sibling notation — full-generation SPECs carry no series notation (the original source of series definitions is the joblist, the spliter's domain). The joblist's "bundles" (physical development units) are never grounds for operations-change judgments.
- **R1 — writing the SPEC is the deriver's procedure.** The lead never edits `spec/SPEC.md` directly. A subagent transitions it via the deriver procedures (the owner is the procedure, not which skill spawned it).
- **Ambiguity is resolved by the lead before delegating.** The incremental/change modes don't negotiate — they presuppose **an already-decided single requirement**. When the requirement is ambiguous (a vague description, or the input document is an undecided lump like a PRD epic), **question/approve with the user before delegating**. Subagents are stateless and can't converse with the user — hand over only clear requirements.
- **File relay.** The subagent records into `spec/SPEC.md` (the deliverable), and the lead reads that file. The agent's session context is never passed — all the lead needs is the result fact "which IDs transitioned", and that is written entirely in SPEC.md. (Identical to the deriver's communication convention: file relay, not real-time messaging; the lead guarantees only order.)
- **The deliverable guarantee comes first.** The subagent reports completion only after finishing the transition with the deriver verifications at PASS. Code never starts on an unverified SPEC (blocking downstream noise).

## Procedure

1. **Input analysis & ambiguity resolution (lead, before delegating)** — read the received request (description or document path) and judge whether it is **a clear single requirement**. The lead's analysis ends here — EARS formalization and ID assignment belong to the deriver procedure (the lead never creates SPEC content, R1).
   - **Addition**: is the new feature a decided single requirement? If vague or several features are mixed, ask the user to split/finalize (an undecided lump like a PRD epic is not a delegation target).
   - **Change/deletion**: fix the target IDs and the change content (modification vs deletion). If which requirement changes how is ambiguous, confirm with the user.
   - When ambiguous, **stop here and question/approve with the user**. Go to 2 only once clear.

2. **Spawn the subagent (lead)** — launch the subagent that performs the transition, passing the following as instructions (stateless, so state every path):
   - **Mode and task**: incremental (addition) or change (modification/deletion) + the requirement content/target IDs (clarified in 1).
   - **Procedure paths**: `.claude/skills/develojt-spec-deriver/references/{incremental-mode.md | change-mode.md}` + `common-rules.md` + `ears-guide.md` (local first — on global installs, `~/.claude/skills/develojt-spec-deriver/references/...`). Follow only these procedures.
   - **Target**: modify `spec/SPEC.md` only.
   - **Constraints**: **never read the joblist or PRD. SPEC only.** **Only for change/deletion (modifying/deleting existing IDs)**, check the impact scope with `scripts/query_chain.py {ID} spec/SPEC.md` (SPEC behavior chains) — an existing ID has chain peers. **Addition (new IDs) never uses the impact reverse-query** — a new ID not yet in any chain has no reverse-query target, and *how* to weave it into existing chains/series is decided by the incremental-mode procedure (LLM dependency assessment). Never use the development-time `query_impact.py` (joblist required).
   - **Completion condition**: repeat until the deriver verifications (`scripts/verify-sections.sh`, `scripts/verify-sources.sh`) PASS, then return a **completion note** — the transitioned IDs (new IDs added / old IDs `[Removed]` / (on modification) new IDs) and the verification PASS status.

3. **Gate check (lead)** — confirm the subagent's completion note and verification PASS. If not PASS or the note is incomplete, **never move to code** — re-spawn once with the same instruction; on repeat failure, report to the user and stop. (Order guarantee = interruption tolerance: code never starts on an unverified SPEC. Even if the agent dies midway, the SPEC holds a partial transition + verification FAIL, so the lead never proceeds.)

3-b. **STORYBOARD sync (lead — only when `design/STORYBOARD.md` exists)** — sync the SPEC transition into the STORYBOARD before moving to code (the order gate extended: SPEC → STORYBOARD → src/. Without this step, a new FR's coverage shortfall and a transitioned FR's staleness are caught by **no verification on this path** and lurk silently — `verify-coverage`/`verify-stale` live only in the mapper gates). Check with `ls design/STORYBOARD.md`; if absent, this step doesn't exist (a builder-appearance-autonomy project — previous behavior unchanged). When entry came through the 'candidate-file input'/'conflict-file input' sections, this step doesn't exist either — those sections' mapper stage (promote/remap) takes this place (no duplicate delegation). Reuse the mapper procedure **as a subagent** (the same pattern as the deriver — not a skill invocation; the lead never writes the STORYBOARD in its place):
   - **Addition**: the promote procedure — path `.claude/skills/develojt-design-mapper/references/promote-mode.md` + `common-rules.md` (local first — on global installs, `~/.claude/skills/develojt-design-mapper/references/...`). In the instruction, **explicitly pass the completion note's new FR ID list as `(no candidate)`** (new-FR enrollment — if the intake classification had confirmed a candidate-queue match, this path wouldn't apply: that's 'candidate adoption'). Target: `design/STORYBOARD.md` (write) · `design/spec-candidates.md` (no-match confirmation — read only).
   - **Change/deletion**: the remap procedure — path `.claude/skills/develojt-design-mapper/references/remap-mode.md` + `common-rules.md` (local first). In the instruction, **explicitly pass the completion note's transition pairs (modification: `old FR → new FR` / deletion: `old FR → (deleted)`)** (no conflict lists — a pure transition sync). If in this change the human also decided that **specific elements' appearance departs from the design originals** (a decision confirmed in step 1 — the originals are the starting baseline, frozen, never edited), pass a **release list** (`SB-NN-MM (appearance-release — reason)` — the lead greps the STORYBOARD by FR ID to list the rows) along with it (remap step 2-b — retirement on record, so the stale mapping rows stop instructing the next worker to restore the old appearance). Target: `design/STORYBOARD.md` only.
   - **Gate**: until the mapper verifications PASS — promote: `verify-anchors` · `verify-coverage` / remap: `verify-anchors` · `verify-coverage` · `verify-stale`. Otherwise re-spawn once with the same instruction; on repeat failure, report to the human and stop (deliverable guarantee — code never starts on an unverified STORYBOARD).

4. **SPEC re-read & implementation (lead, via file relay)** — the lead greps `spec/SPEC.md` directly to read the transitioned IDs (from the file, not agent context), and carries them into code **following develojt-code-builder SKILL.md's five essentials (traceability, wiring, constraints, leanness, separation)** (the single truth of code implementation/sync logic is that skill — never copied into this document. If `spec/ARCHITECTURE.md` (the structure contract) exists, read it in full before implementing and comply with its layers/dependency directions/placement — the same contract as builder essentials 3·4. An implementation possible only by changing the contract: unilateral revision forbidden — get the revision proposal (what → what · reason · application scope) finalized by the human and record the revision-history line before proceeding, the same rule as the builder's 'when a design change is needed' structure paragraph. Without a contract, as before):
   - **Appearance-consumption judgment (before implementing — translated reproduction is an approval gate)**: if this change creates or alters `design/`-baseline appearance, judge before implementing whether the design source's language/format is valid as-is in the tech stack (the same contract as builder essential 3 — judged per language/format, ambiguous → translated reproduction). For **use as-is**, state that fact in the completion report and proceed (no extra approval). For **translated reproduction, do not start implementing** — report the verdict "stack mismatch (design X ↔ stack Y) — translated reproduction" to the human and implement only after approval — builder essential 3's "report (workflow 3) approval" points at the new-development path's report, so on the operations path this gate takes its place (the same gate as builder's pre-implementation report approval, development/operations symmetry).
   - **Addition / change (modification)**: implement the new IDs (`@spec`, wiring, constraints, leanness — including appearance compliance when `design/` exists; compliance rule per the builder's essential 3: every file inside design/ in its own role — README mandatory → screen sources → screenshots as the fallback + companion-asset consulting and asset use (seed/mock data reproduced content-as-is — no unilateral real-data substitution; real-data wiring only when the element's FR behavior chain requires it: the builder's essential-3 'decoration/seed data' paragraph) + appearance-code consumption per the judgment above (stack match → use as-is; mismatch or ambiguous → translated reproduction); the candidate queue and conflicts file are never followed). For modifications, remove the old ID's `@spec` tags and dead code — the old ID is `[Removed]` in the SPEC, so `verify_spec_coverage` catches it as an orphan and forces the cleanup.
   - **Change (deletion)**: remove the `[Removed]` old ID's `@spec` tags and dead code.
   - After implementing, run the builder's 4 self-checks (existence/format) and confirm PASS (`.claude/skills/develojt-code-builder/scripts/verify_{refs,todo,spec_coverage,comments}.py` — global installs: `~/.claude/skills/...`), **plus the 3 machine floor checks**: `python3 .claude/skills/develojt-code-pdca/scripts/verify_security.py src/ --root-config` · `python3 .claude/skills/develojt-code-pdca/scripts/verify_enforced_rules.py src/` · `python3 .claude/skills/develojt-code-pdca/scripts/verify_architecture.py src/` (global installs: `~/.claude/skills/...` — reusing pdca C2·C3·C4's candidate detectors, so the operations path passes the same security, enforced-rule, and structure-contract floors as the development phase. Without the enforced-rules file `.claude/rules/enforced-rules.md` or the structure contract `spec/ARCHITECTURE.md`, the corresponding script prints 'not applicable' — proceed as-is). **Run the boot gate as well**: `python3 .claude/skills/develojt-code-builder/scripts/verify_boot.py spec/run-profile.md` (confirming the releasable invariant still holds — even after an operations change, "it builds and it boots" must not break. Without a run profile it is not applicable and PASSes; FAIL and exit 2 are handled exactly by builder workflow 5's boot-gate rules — never alter the profile to pass the gate). **If even one candidate appears, a develojt-code-pdca recheck is mandatory** — candidate judgment belongs to the pdca checker's C2·C3·C4 procedures (the lead never judges or rejects candidates itself — no self-grading). Even with zero candidates, if static completeness was affected, recheck via develojt-code-pdca (passing the scope as the target FR ID list).
   - **Human screen comparison (the appearance gate)**: if this change created or altered `design/`-baseline appearance (promoted/incorporated anchors and STORYBOARD-mapped UI are the targets — appearance outside the design mapping, like a conflict-B (SPEC-baseline) correction, is not), put a screen-comparison table in the completion report: one line per changed screen — `running screen (how to reach it) ↔ design baseline (design/screenshots/{file} · screen-source element · README section) ↔ reproduced anchors (SB-…)` — then request the human eye comparison. **Until the confirmation answer arrives, the change is not treated as complete** (text gates and pdca cannot, in principle, judge appearance — the same human-eye gate as builder workflow 7: the operations path compares immediately because the system is running, while the development path registers into the screen-review ledger for one batch session). **If this fix was taken in from builder's screen-comparison session** (after full implementation completion, every fix belongs to this skill), then after this comparison confirmation set the corresponding `spec/screen-review.md` row to `Confirmed` and return to the session. If the app cannot be run yet, state that fact in the completion report.

## Candidate-file input — mapper promote integration (classification: candidate adoption)

When the intake input is **the candidate file (`design/spec-candidates.md`)** or names its candidates, run the deriver delegation above (procedures 1–4) **as the unchanged base** and splice the mapper promote delegation in between (this section's promote stage takes the place of base step 3-b — no duplicate 3-b run). When the input is unrelated to candidates (free description, ordinary documents), this section does not apply — only the existing procedure runs (**side effect 0**).

> The trigger is **whether the input points at candidates (the file or UI IDs)** — a branch on input content, not a separate classification signal.
> Flow: candidate analysis & adoption → ① deriver (SPEC recording) → gate → ② mapper promote (STORYBOARD writing) → gate → ③ code.

**Only the differences added onto the existing procedure:**

1. **Added to procedure 1 — candidate analysis & adoption confirmation** — the lead reads `design/spec-candidates.md`, **lists** the candidates (UI ID, anchors, implied behavior), and **confirms the adoption scope with the human** (all/some). **Adoption is the human's decision** (design-philosophy principle 3 — `[Decorative]` is not an adoption target (only not subject to requirement-ization — it remains the builder's appearance-reproduction target: mapper common-rules §4); subagents can't converse with the user). Only the confirmed adoptions are handed to the deriver as single requirements.

2. **Procedures 2–3 as-is — deriver delegation + gate** — record the adopted candidates into the SPEC via the deriver incremental procedure and confirm verification PASS. Keep the **`candidate UI ID ↔ new FR ID` pairs** from the deriver's completion note (the input to pass to the mapper).

3. **A stage spliced after procedure 3 — mapper promote delegation** — after the deriver gate PASS, **reuse the mapper promote procedure via a subagent** (the mapper too is `disable-model-invocation` — the same pattern as the deriver, not a skill invocation):
   - Procedure paths: `.claude/skills/develojt-design-mapper/references/promote-mode.md` + `common-rules.md` (local first — on global installs, `~/.claude/skills/develojt-design-mapper/references/...`).
   - Targets: `design/STORYBOARD.md` and `design/spec-candidates.md` only. **Explicitly pass the `candidate UI ID ↔ new FR ID` pairs** in the instruction (so the mapper never guess-matches — a promote-mode entry condition).
   - **Gate**: until the mapper verifications (`verify-anchors`, `verify-coverage`) PASS. Otherwise re-spawn once with the same instruction; on repeat failure, report to the human and stop (deliverable guarantee — code never starts on an unverified STORYBOARD).

4. **Procedure 4 as-is — through code by default** — after the STORYBOARD is in order, implement the new FRs (a received change completes through code by default). **But if the human separately instructs "up to the STORYBOARD"**, stop before implementation and report there.

> **Files read**: this branch reads `design/spec-candidates.md` and `design/STORYBOARD.md` beyond the SPEC (the candidate-adoption context — the operations-phase 'SPEC only' exception is limited to design/ deliverables). The joblist and PRD are still never consulted.
> **Forbidden in this branch**: never adopt all candidates unilaterally without human confirmation (the lead goes as far as listing; adoption is the human's). Never omit the `candidate UI ID ↔ new FR ID` pairs from the mapper delegation. The lead never writes the STORYBOARD directly (mapper procedures only — R&R).

## Conflict-file input — applying conflict verdicts (classification: conflict resolution)

When the intake input is **the conflict file (`design/spec-conflicts.md`)** or names its conflicts (conflict N, UI IDs), follow this section. Whether the requirement changes is decided not by the input form but by **the human's per-conflict A/B decision** — A (design wins) = the SPEC changes (the 'change/deletion' base above); B (SPEC wins) = the SPEC is invariant. When the input is unrelated to conflicts, this section does not apply (**side effect 0**).

> Flow: conflict listing & A/B confirmation → [if any A] ① deriver change (violated-FR transition) → gate → ② mapper remap (replacement + A incorporation + B cleanup) → gate → ③ code.
> B-only means no ① — remap (header refresh & resolved-section cleanup only) → code check/correction.
> This section's remap stage takes the place of base step 3-b — no duplicate 3-b run.

**Only the differences added onto the existing procedure:**

1. **Added to procedure 1 — conflict listing & decision confirmation** — the lead reads `design/spec-conflicts.md`, **lists** the conflicts (conflict N · UI ID · violated FR · recommendation), and **confirms the per-conflict A/B decision with the human** (re-confirmed at the intake gate even when the file's decision cells are filled — the only misfire defense. The verdict belongs to the human). For conflicts violating the same FR, present the "one-direction grouping" recommendation (the decision is the human's). **For confirmed As, finalize the new requirement content with the human per violated FR** — the transition unit = the FR (several conflicts violating the same FR = 1 transition; a conflict violating several FRs = several transitions).

2. **Procedures 2–3 as-is — deriver change delegation for confirmed As only + gate** — delegate the violated FRs' modification (T3 — old FR `[Removed]` + new FR) via change mode and confirm verification PASS. Keep the **`old FR ID → new FR ID` pairs** from the deriver's completion note (the input to pass to remap). If only Bs were received, this stage doesn't exist.

3. **A stage spliced after procedure 3 — mapper remap delegation** — after the deriver gate PASS (B-only: immediately), **reuse the mapper's mapping-update procedure via a subagent** (the same pattern as promote — not a skill invocation):
   - Procedure paths: `.claude/skills/develojt-design-mapper/references/remap-mode.md` + `common-rules.md` (local first — on global installs, `~/.claude/skills/develojt-design-mapper/references/...`).
   - Targets: `design/STORYBOARD.md` and `design/spec-conflicts.md` only. **Explicitly pass the transition pairs (A: `old FR → new FR`), the conflict incorporation list (A: `conflict N · UI ID ↔ new FR ID`), and the cleanup list (B: `conflict N`)** in the instruction (no guess matching — a remap-mode entry condition). With B-only and no transitions, remap does only header refreshes and resolved-section cleanup.
   - **Gate**: until the mapper verifications (`verify-anchors`, `verify-coverage`, `verify-stale`) PASS. Otherwise re-spawn once with the same instruction; on repeat failure, report to the human and stop. A `verify-coverage` FAIL right after the transition and before remap is **an intended intermediate state** (the new FR isn't in the body yet — isomorphic to change-mode step 9's "the FAIL forces the cleanup"). The lead never fixes the STORYBOARD in the mapper's place.

4. **Procedure 4's code — A and B in one pass** — **A**: implement the new FRs (appearance via the incorporated STORYBOARD rows' anchors — the builder's five essentials). **B**: confirm the code conforms to the (invariant) SPEC and correct any violations — the conflicting UI was never in the body mapping, so being unimplemented is normal under the builder contract (the confirmation result is itself the deliverable). Cleaning the old FRs' `@spec` tags and dead code follows the base procedure (the coverage orphan gate forces it). In projects with no code yet (conflict resolution mid-development), leave implementation to the builder and state so in the completion report — the STORYBOARD is already updated, so the builder implements normally afterwards.

> **Files read**: this branch reads `design/spec-conflicts.md` and `design/STORYBOARD.md` beyond the SPEC (the operations-phase 'SPEC only' exception is limited to design/ deliverables — same as candidate-file input). The joblist and PRD are still never consulted.
> **Forbidden in this branch**: never delegate conflicts with undecided A/B (the verdict is the human's — fixed at intake). Never omit the incorporation/cleanup lists from the remap delegation. The lead never writes the STORYBOARD or the conflict file directly (mapper procedures only — R&R).

## Forbidden

- **The lead never edits `spec/SPEC.md` directly** — transitions happen only via deriver procedures (subagents) (R1).
- **Never give subagents the joblist/PRD or have them read those** — the operations phase is SPEC only.
- **Never delegate an ambiguous requirement** — the lead resolves it with the user before delegating (incremental/change are negotiation-free modes).
- **Never try to invoke the deriver/design-mapper "skills"** — they carry `disable-model-invocation` and can't be called. Perform via subagents following the procedure documents.
- **Never start code without a verification-PASS note** — the deliverable guarantee comes first.
- **Never update the spliter/joblist** — the operations phase has no joblist (lifecycle over). Only SPEC↔code is reconciled.
