## Report & approval gate (forced — honor this before anything else)

> **Look at the arguments first.** If a modification flag like `--review`, `--change`, or `--add` appears in the arguments, this is not this skill's job — write nothing, explain, and exit: "Operations-phase change intake is the develojt-code-changer skill. Please state your request as-is to develojt-code-changer." Only when no flag is present, follow the order below.
>
> **On a structure-contract lifecycle instruction** (the arguments/request target the contract itself, not code — mid-project adoption "set up the structure contract" / revision "change the structure to …" / migration "run the structure migration") this invocation's scope is that work — follow the `references/architecture-lifecycle.md` procedure (**loaded only on that instruction**). Its report/finalization gates use that procedure's format, but the principle here holds unchanged: no writes before human finalization.

The order is always this: **assess state (read-only) → print the report → stop → user approval → implement.**

- Before printing the report, and before the user's approval response arrives, **write tools (Edit, Write, file creation) are forbidden.** Only reads (ls, grep, Read) are allowed. Starting implementation without the report is a violation.
- "Continue" / "keep going" is **a skill invocation, not an approval.** Even then, print the report, stop, and wait for approval.
- However, an affirmative answer to the scope-explicit question the builder asked in workflow step 7 ("continue with the next bundle N / EP-YY?") counts as **explicit approval of the specific scope named in that question**.
- **Entering develojt-code-pdca after a bundle's implementation is not subject to approval** — inspection and reinforcement are part of implementation, so proceed automatically without asking (workflow 6·7). The approval gate binds "what to implement (the scope)", **the verdict when the appearance-consumption mode is 'translated reproduction'** (essential 3), and **a new project's first-report structure-contract draft** (workflow 1 — approving that report finalizes the contract; finalizing a lifecycle instruction's adoption draft, revision proposal, or migration staging plan follows the same grammar — references/architecture-lifecycle.md).
- The only exception: when the user, **in this very message**, explicitly waives approval with a concrete scope ("go straight to bundle 9, don't ask", "do it all, don't ask"), print the report and implement immediately.

Every SPEC requirement traces its source back to the human epics in the PRD.
This skill's `@spec` tags are the last link of that chain — a missing tag severs the whole traceability chain.

The human gives the What (requirements); AI autonomously builds the How (code).
This skill never blocks that autonomy — it is a **harness enforcing only the five essentials**.
The five below are everything. Whatever is not here is AI autonomy, and no separate "don't do" list exists —
keep the essentials and the rest follows.

## The five essentials

1. **Traceability** — every implementation carries a `@spec` tag.
2. **Wiring** — the SPEC's behavior chains are actually connected (every outcome reached).
3. **Constraint compliance** — tech stack, forbidden libraries, and specified failure behaviors kept exactly.
4. **Leanness** — only the code that is strictly needed. Structure, patterns, algorithms, paradigms: AI autonomy (within the structure contract when one exists — essential 3).
5. **Separation** — never self-grades whether behavior is correct. Implementation and wiring are where this skill ends.

Without it, structure is entirely AI autonomy (as before), and **a new project's (no src/) first invocation composes the draft and finalizes it by report approval** (workflow 1 & the report template). - **Tech stack = SPEC Document Info** — *what to build with* (language, framework, forbidden libraries).
- **Progress ledger = `spec/joblist.md`** (if present) — how far we got / what's next / what notes exist.
- **Appearance baseline = `design/`** (if present) — *how it looks* for UI-implementing FRs. **Every file in the folder is part of the design intent — follow them all, each in its own role** (essential 3 — the priority is only a baseline fallback: an upper asset never replaces a lower one, and the type list is not a closed list): ① if `README.md` exists, **compliance is mandatory** (read it in full) ② without it, consult the design files present, such as screen sources ③ screenshots only → follow the screenshots as far as they go. **+ Companion assets** (files the screen source loads or references — runtime/helper `support.js` etc., stylesheets, fonts, icons, images, mock data) are the original source of behavior/effect/appearance meaning — consult them whenever reproducing (mock/seed data is a reproduction target down to its content — no unilateral real-data substitution, essential 3), and use static assets as-is regardless of whether the source references them (essential 3 — text-based assets after the executable-code check). `STORYBOARD.md` (if present) is the tracing bridge for finding the mapped UI — grep it by FR ID (read-only — the originals are the starting baseline, frozen; an appearance different from the originals goes only through a human-decided release: essential 3). But the mapper deliverables — the candidate queue and the conflicts file — are not appearance norms: never follow them (essential 3). Appearance-code consumption: on a stack match, using the source as-is is the default; on a mismatch, translated reproduction (subject to approval) — essential 3. Without `design/`, the SPEC alone.
- Structural design documents and the PRD are not inputs (the structure contract `spec/ARCHITECTURE.md` is the one exception — the item above). Module/class/dependency structure is decided by AI while coding (within the contract's structural decisions when one exists — essentials 3·4).
- **Code root = `src/` (pipeline convention)** — whatever the language ecosystem's habits, tracing (grep) and the verification scripts look at `src/`. The substructure inside is free.

## Essential 1 — traceability: @spec tags

`@spec` is the only tracing means linking the SPEC and the code. `grep -r "@spec FR-05-001" src/` finds the implementation site.
**No @spec = unimplemented, even if the code exists.** When one requirement spans several functions, tag them all.

Format (language-agnostic; this is the foundation of tracing and maintenance):
- In the comment block **directly above** the function/class declaration. Inside the body (docstring, inline) forbidden.
- **One per line, ID only.** Comma-multiples (`@spec A, B`) and mixed descriptions forbidden. A blank line between the description and the @spec lines.

```javascript
/**
 * Records the order to persistent storage
 *
 * @spec FR-05-001
 * @spec NFR-00-004
 */
function saveOrder(order) { ... }
```

The comment language follows the convention — `comment-language` in `.claude/rules/code-conventions.md` (korean|english; english when the item/file is absent). english: write comments in English (the SPEC is English → design and code terminology stay aligned). korean: write comments in Korean (technical terms and proper nouns stay in English).

## Essential 2 — wiring: behavior chains

The SPEC's **Observable Behavior Chain** tables say "this trigger must produce these outcomes **together**".
With every function present but the trigger never reaching the outcomes, it builds but doesn't behave — this is the gap to block.

**When implementing a trigger, actually connect every outcome in the chain table.** The connection method (direct calls, events, callbacks, DI) is free. The outcomes just have to **all be reached**.

> e.g., if the chain is "valid order created → stored + 201 response + confirmation event", the creation path must reach all three. One missing = incomplete.

**When a trigger or target is a sweeping expression, every occurrence site is a connection target.** When a requirement's (EARS sentence, chain table) trigger or target is a sweeping expression such as "all", "every", or "whenever X occurs", find every site and path in the code where that class occurs, and connect each site so it reaches the response/outcome — connecting only some sites is not `[Free]` but incomplete (`[Free]` delegates the value/method, never shrinks the application set). The checker's verdict criterion is the same (pdca checker-rules 'Sweeping expressions mean exhaustive coverage' — this paragraph puts that criterion into words on the front-door side).

## Essentials 3·4 — constraints and leanness

**Free (AI decides):** file/module organization, signatures, data structures, algorithms, patterns, paradigms. **Form must never outgrow the essentials.** But with `spec/ARCHITECTURE.md` (the structure contract) present, layers, dependency directions, and placement follow the contract — the freedom lives inside it (the constraint below. The autonomy that collapses things was never "AI decides" but "each session decides again, on its own" — global decisions belong to the contract, details stay autonomous).

**Constraints (mandatory):**
- `[Free: reason]` notation → AI decides the value. **It is not an omission. Don't stop — decide reasonably.**
- **Structure contract (when `spec/ARCHITECTURE.md` exists) → follow the layer map, dependency directions, and placement rules as-is.** Put code where the contract places it (layer, folder, home for shared code), and create no import/reference in a forbidden direction. **Code that has no place in the contract, or an implementation possible only by changing the contract: unilateral placement and unilateral revision are forbidden** — stop and report ('when a design change is needed'. The failure direction goes to a question, not silent deviation — the same rule as appearance). Without a contract this constraint does not exist (structure fully autonomous — as before).
- **Tech stack & forbidden libraries** → no violations or unilateral substitutions. Tool facts like initialization/boot order are right or wrong — get them exact.
- **Appearance (when `design/` exists) → follow the design as-is (not as reference).** **The design/ originals are the project's starting baseline and are frozen — this skill never edits them. An appearance different from the originals is legitimate only for elements the human explicitly instructed and approved (a release — the mapper's remap retires that mapping row into a `[No UI]` appearance-autonomy transition on record: the 'when a design change is needed' section), and a released element's appearance baseline is thereafter the human instruction and the implemented code, not the originals. Deviation on the builder's own judgment remains forbidden.** **Every file inside design/ is part of the design intent — ignore none of them: determine each file's role and follow it in that role** (the type list below is a representative classification, not a closed list). Compliance priority across the design assets (top-down; whatever exists is the baseline — **a fallback, not a replacement: every asset present is consulted in its own role**):
  1. **If `design/README.md` (the design guide) exists, compliance is mandatory** — **re-read it in full at the start of every bundle that contains UI FRs** (a small normative document — not subject to the no-full-reads rule. Not once per skill invocation: as bundles and PDCA cycles pile up, context compaction erases norms read early on — the per-bundle re-read is the defense against that). It is the original source of the global norms that anchor greps never catch — design tokens (colors, typography, spacing), global layout, interactions, reproduction guidance — and it applies not only to mapped UI but **to newly created UI as well**.
  2. Without a README → consult the design files present, such as screen sources (`.dc.html` etc.), and follow the appearance.
  3. No screen sources either, screenshots only → follow the screenshots as far as they go.

  **+ Companion assets — files inside design/ that the screen source loads or references (runtime/helper `support.js` etc., stylesheets, fonts, icons, images, mock data — whatever the source's load/reference declarations point at: `<script src>`, `<link href>`, `@import`, `url()`, fetch, and the like). When present, always consult them when reproducing behaviors/effects (not a fallback — read them alongside the screen source).** They are the original source of what the source's declarations and expressions *actually do and look like* (state, event, props semantics; style rules) — without these files, the source markup alone will not reproduce identical results. **Static assets (images, icons, fonts, logos) go beyond consulting: use them in the deliverable as-is** (no recreation, no unilateral substitution — they are assets, not code, so they are always used as-is regardless of the consumption-mode verdict). **Mock/seed data too goes beyond consulting: its content is a reproduction target** (no unilateral real-data substitution — real-data wiring only when the element's FR behavior chain requires it: the 'decoration/seed data' paragraph below). Files the README labels "viewer-only / not production" are **excluded from as-is use only** (those elements take the translated-reproduction path — not no-consult, not no-semantics-check, not no-asset-use). Consulting locates via grep, but **the parts that define the appearance/behavior of the element being implemented now (that element's style-rule block, the functions that element uses — when such a function delegates appearance/behavior values to yet another function, follow the delegation chain and read down to the body where the values are actually decided) are actually Read** — what's forbidden is the whole-file Read that sweeps in unrelated parts (element-level partial reading is a duty). **Existence is confirmed via double net**: ① check the screen source's load/reference declarations directly (1st — workflow 1) ② if `design/STORYBOARD.md` exists, check the **shared technical assets** row in its Document Info (2nd — one `grep "Shared technical assets" design/STORYBOARD.md` line, not a full read; the mapper's persistent record catches assets the 1st net missed).

  If `design/STORYBOARD.md` exists (the FR↔UI tracing bridge): for a UI-implementing FR, grep the STORYBOARD by that FR ID (when the joblist row's Notes already carry an `Appearance: SB-…` anchor, that anchor is this row's reproduction scope — the grep is reinforcement). When a mapped UI row hits, **the source anchor is for locating only — actually Read the source region of the element the anchor found (the markup, plus the style rules and script behavior that define that element) and implement its appearance (layout, elements, colors, state variants, motion, data source — the 'decoration/seed data' paragraph below) as-is** (the professional design is the source of truth for appearance — unilateral changes and simplification forbidden. Guessing the whole from a few grepped lines and re-creating it inevitably simplifies — the cause of "compliance only as far as sight reaches", hence forbidden). If no row hits or it's `[No UI]`, that FR's appearance is autonomous within the norms of the priority above (a `[No UI]` row marked **appearance-autonomy transition (human-decided release)** is not a restore-to-originals target — its baseline is the human instruction at release time and the existing implemented code, and when the README's global norms conflict with the human instruction, the human instruction wins). **An element whose Mapped FR cell is `[Decorative]` has no SPEC requirement — that is not an exemption from reproduction** — it is part of the design, so it is not skipped as "no implementation grounds since it's not in the SPEC"; it is reproduced together when implementing the UI FRs of the screen it belongs to (when carried on an appearance anchor it is part of the row's completion condition — workflow 4. Even without an anchor, decorations visible in the screen source or screenshots are the same reproduction target). **Without a STORYBOARD at all (mapper not run), the sight rule is the same** — find the element being implemented directly in the screen source (unique-text/class grep — the anchor's stand-in) and actually Read that element's source region to reproduce it as-is. If `design/` itself is absent, implement from the SPEC alone (side effect 0). **But how that appearance code is consumed is decided by whether the stacks match (judged in workflow 1, stated in the report — the judgment is per language/format: not the design package as a whole — a mix can occur, like the markup mismatching while the stylesheets match, and a mix is stated with both verdicts in the report)**: ① **when the design source's language/format is valid as-is in the project's tech stack (HTML→HTML, CSS→CSS, etc.), using that element's source as-is is the default** — rewriting the same thing inevitably makes it different, so **unilateral rewriting and paraphrasing are forbidden**. The writing rules in `.claude/rules/` (naming, formatting) are no grounds for rewriting either (use-as-is wins — the only exception is the security floor, the asset executable-code check). Only the minimal touch-ups integration requires (paths, selector-collision fixes, @spec tags, removing viewer wrappers the README excluded) are allowed; state the as-is use in the report and proceed (no extra approval — the asset executable-code check still applies). ② **When the tech stack differs and the source cannot be used as-is, read the element in full and reproduce it translated into the tech stack — reproduction is subject to approval**: state the verdict "stack mismatch (design X ↔ stack Y) — translated reproduction" in the report (workflow 3), and implement only after that report is approved (if the verdict flips after the report — planned as-is use turns out to need reproduction — stop implementing and re-report). **When the match is ambiguous (no confidence the source is valid as-is), judge it as translated reproduction** — when the verdict could fork, the failure direction goes to an approval question, not to unapproved use. In either mode, **making it up without reading is forbidden** — actually Reading the element's source region in full is the common duty.

  **The origin of decoration/seed data is appearance too — reproduce the design seed as-is; never substitute real data unilaterally.** When the design source shows an element filled with seed/mock data (demo graphs, example lists, placeholder values, …), that data is part of the reproduction target — carry the source's seed over as-is and do not swap in another origin (live queries, a backend, real-data lookups) ("we have a real backend, so real data is better" is not an improvement — it is an appearance deviation). **Real-data wiring happens only when the SPEC requires it, and the criterion is not keywords but the behavior chain of the FR carried by that element**: if the chain fetches/produces and delivers that displayed data, real data; if the chain says nothing about that data's origin, design seed. When the Mapped FR cell is `[Decorative]`, it is always the design seed — **decoration makes no data claim**: tying pure decoration (background graphs, meshes, particles, …) to real data so it goes empty or changes when data is absent is itself an appearance violation. On a path without a STORYBOARD, make the same judgment against the SPEC requirement corresponding to that element instead of the FR cell. **If it is still ambiguous, judge it as design seed and state it on the report's data-source line (workflow 3)** — the failure direction goes to the visible seed (surfaced in the report and the screen comparison, where a human catches it), not to unapproved real-data wiring (an invisible dependency — empty or different when data is absent).

  **Files beyond the types above are not ignored either** — normative documents (guides, manuals) are complied with like ①, screen-source-like files like ②, full-screen captures (screenshot-like files) serve as the baseline like ③, and files the screen source loads or references are treated as companion assets. **Asset files that become parts of the deliverable (icons, logos, fonts, illustrations, images, etc.) are used as-is — never recreated — regardless of whether the source references them**: a screenshot is a reference photo of the screen, reproduced by looking at it; an asset is a part of the screen, dropped in as-is (this holds equally for packages with no screen source at all — screenshots plus an asset bundle only). A file whose role cannot be determined is never ignored — state it in the report (the human decides its role; once the human writes that role into `design/README.md`, it is consumed as ① from the next bundle on and the re-reporting ends). **But the files never followed — `design/spec-candidates.md` (unadopted candidates: not in the SPEC, so implementing them is forbidden; adoption goes through develojt-code-changer), `design/spec-conflicts.md` (design↔SPEC conflicts: awaiting human judgment — never preempt either side), and the mapper's intermediate artifacts (`inventory.md`, `map-*`, `review-*`, `{deliverable}-{role}.md` — leftovers of an abnormal stop)**: these are mapping deliverables and queues, not appearance norms (following them means bypassing the SPEC or preempting human judgment — an R&R violation).

  **Executable-code check for assets entering the deliverable (all types)**: text-based assets that can carry executable code (SVG and the like) are checked for embedded executable code before being dropped in — a surface check on the level of `grep -rilE '<script|javascript:|on(load|error|click)=' design/ --include='*.svg'` (not a full read — workflow step 1's collection script `scan_design_assets.py` prints this check). If it hits, that file is NOT dropped in as-is — state it in the report; the disposition (use after removing the code / use as-is / exclude) is the human's decision (security is a floor and is never relaxed by appearance compliance — same as the rules priority). "Use as-is" applies to assets that passed this check.
- **A first use of an external technology is confirmed against the installed reality, and recorded — memory is not research** → ① **Delegated adoption**: when adopting a framework/major library/model the SPEC delegated as "unspecified (proposals allowed)", immediately leave one line, `name version adopted`, in that joblist row's Notes (so the next session knows without grepping the code). ② **First-use confirmation** (delegated adoptions and SPEC-named technologies alike): when this bundle **imports/calls an external framework, major library, or model for the first time** (the determination is mechanical — no `confirmed`/`adopted` record in the joblist Notes and no use in the existing code means first), confirm the APIs you'll use — existence and signatures — against the installed reality (the installed package's type definitions, bundled docs, `--help`) before implementing. **Not "when uncertain" — always** — self-judging uncertainty is overconfidence's doorway (guess-based API usage is forbidden). After confirming, leave one line, `name version confirmed`, in that joblist row's Notes (the record is the once-only evidence — no re-confirmation for the same technology). **When local confirmation is impossible and web docs are needed, stop and report** — name what you would go out to confirm, and consult the web only after human approval (exploration outside the project requires prior approval). **A technology that is not installed is never papered over with an unauthorized install** — follow the ladder of the resource-acquisition protocol (`rules/resource-acquisition.md`): local reality check → web research → install, human approval at every rung.
- **If/Unwanted failure behaviors** → must be implemented. Drop decorative/speculative defensive code, but **never drop specified failure handling.**

## Essential 5 — separation: no self-grading

Judging "does this code run as required / do the chains actually reach" happens **outside this skill**.
A coder grading their own code can't see their own blind spots. This skill ends at implementation and wiring.
The same holds for appearance — **the final judge of appearance is the human eye** (workflow 7 — each bundle registers into the screen-review ledger, and after full implementation completion every row must pass human-eye comparison, one item at a time, in the screen-comparison session before the development draft is complete). Text gates and self-reports cannot, in principle, judge appearance.

## Workflow

> The below is **for new implementation only**. Operations-phase requirement/code changes are received by the develojt-code-changer skill (see the guidance rule in the report & approval gate).

1. **Assess state (lightly)**
   - `ls src/` for new/existing, `grep "Tech stack" spec/SPEC.md` for the language, check `.claude/rules/` if present.
   - If `spec/ARCHITECTURE.md` (the structure contract) exists, **read it in full** (a small norm document — not subject to the no-whole-reads rule. Compliance mandatory — essentials 3·4). If absent and **src/ is also absent (a new project), compose the contract draft to carry in this first report** — **before composing, read `spec/SPEC.md` in full** (the contract is a one-time deliverable that sets the structural baseline for the project's whole life — its input is the full body of requirements, not a partial view. ## When a design change is needed

`[Free]` items and method-internal implementation (error handling, helpers, imports, type conversions) proceed without reporting.
But **when the requirement itself must change, or a feature absent from the SPEC is needed**, never slip it into the code — the problem is the SPEC (intent), not the code. During new implementation, stop and report — once the human confirms the addition/change, the development-phase (joblist in progress) route is the develojt-spec-deriver procedures (addition = incremental mode · modification/deletion = change mode) → develojt-spec-spliter incremental (ledger enrollment). Not develojt-code-changer: that skill is the operations-phase (post-development) front door and never reads the joblist — received mid-development, the new requirement lands in the SPEC only and is never assigned in the ledger. For an intended operations-phase change, take it to the develojt-code-changer skill (when the requirement changes, that skill first transitions the SPEC via the deriver procedures — R1).

**External-consumer interfaces are the same — for an interface that something outside this repository's code builds against (an API that other programs call, command arguments and exit codes that people or scripts supply, file and message formats that other systems read and write, public function signatures that outside developers use, etc.), its shape (paths, commands, field names, headers, error codes, formats) is a requirement the SPEC has finalized as rows with IDs** (the deriver boundary rule — that shape is behavior observed from outside, so it is neither `[Free]` nor "method-internal implementation"). If, during implementation, a field, endpoint, or command absent from the SPEC must be added, or something must be built differently from the SPEC's names or shape, that is not an implementation detail but the first paragraph's "feature absent from the SPEC · requirement change" above — never add or change it quietly; stop and report (the route is the same as in the first paragraph: during development, deriver addition/change → spliter incremental; during operations, develojt-code-changer). Internal interfaces used only by screens and modules inside this repository are outside this paragraph — autonomous as before (within the structure contract, if there is one).

**The tech stack is the same — a finalized technology is a decision not only in the code but also in reports, approval requests, and answers to questions** (essential 3's "no violations or unilateral substitutions" applies to words too). When the implementer lists or recommends alternatives outside the contract for a technology the SPEC Document Info tech stack has finalized (language, framework, library, model — items delegated as "unspecified (proposals allowed)" belong to essential 3's delegated adoption and are outside this paragraph), that itself reopens what was finalized — do not do it: ① an install/acquisition approval request (resource-acquisition protocol rung 3) is a place to ask not "what should we use" but "may we bring in what has been decided" ② when the human asks about substitutability, the answer stays within the contract (possible/impossible and the grounds — options outside the contract are not raised. If the human explicitly instructs a review of alternatives itself, comply, but adoption still goes through human finalization + a SPEC transition) ③ listing cost facts such as install size and dependency burden is good reporting, but presenting alternatives on the grounds of those facts is forbidden (optimizing for cost or simplicity is no reason for the implementer to shake the contract — code-conventions §4's "only strictly necessary dependencies" is also a principle for discretionary choices, not grounds for reducing finalized technologies). The only legitimate entrance to reopening is **a measured impossibility** — when an actually encountered fact such as an install failure, a missing required API, or a license conflict blocks a finalized technology, do not pick an alternative; stop and report only that fact (once the human finalizes, the path is the same as above — deriver change → spliter incremental). A prejudgment ("it will be large", "it may fail") is not an impossibility.

**Appearance is the same — when the human, mid-implementation, instructs an appearance for a mapped UI that departs from the design originals** (requirement invariant), never change it quietly; **the release comes first**: ① state in the report that the instruction departs from the originals (if it could also be read as staying within the originals, confirm with the human — the failure direction goes to a question, not to silent deviation) ② run the mapper remap procedure as a subagent to retire the mapping row — path `.claude/skills/develojt-design-mapper/references/remap-mode.md` + `common-rules.md` (global installs: `~/.claude/skills/...`), **explicitly passing the release list `SB-NN-MM (appearance-release — reason)`**, gated on `verify-anchors` · `verify-coverage` · `verify-stale` PASS (one re-spawn; on repeat failure report and stop). Workflow 4's "the lead does it directly" is about implementation). **If `spec/joblist.md` exists, the lead then cleans up the ledger anchors** — grep the joblist for the released SB ID, remove that SB from the `Appearance:` list in the Notes of the row carrying it (an SB shared by several FRs rides only on the front-most row in the ledger, so it may not be the released element's own FR row), write `(SB-NN-MM released — reason)` at the end of the list, and confirm `python3 .claude/skills/develojt-spec-spliter/scripts/verify_anchor_sync.py spec/joblist.md design/STORYBOARD.md` (global installs: `~/.claude/skills/...`) PASSes — that gate catches an anchor pointing at a retired row as a ghost, and since the mapper never looks at the joblist and the spliter never enters without a SPEC transition, this is the only cleanup point. Writing the Notes cell is within this skill's existing scope (workflow 4 — rows, order, and series unchanged. An SB ID inside a parenthesized note is not an anchor — the same place as deferral-handover notes). ③ then implement per the instruction. From then on that element's appearance baseline is the human instruction and the implemented code (the screen-review ledger's design-baseline cell also says "human instruction (release)" instead of the originals — workflow 7). The design/ originals are the starting baseline — frozen: never edit them to match, in any case. In a project without a STORYBOARD there is no mapping to release — the instruction itself is the baseline, so state it in the report and implement as-is.

**Structure is the same — when, mid-implementation, code has no place in the structure contract (`spec/ARCHITECTURE.md`) or an implementation is possible only by changing the contract** (a new layer is needed, no allowed direction can wire it, …), never place it quietly — stop and report. But **"possible only by changing it" is the result of a review, not a first verdict — revision is the last resort**: first review whether it can be wired within the allowed directions by in-contract means (relocation to a shared place the contract sets, dependency inversion/interface injection (a consumer-side declaration + injection at the assembly point), value parameterization, etc. — patterns already in the project first), and the grounds for the verdict are not a category convention ("this concern belongs in this layer by nature") but **that code's reality** (read the actual imports and calls — does a dependency that blocks the existing place really exist). Only when it is still impossible after exhausting them is it a revision, and then: ① state in the report which rule leaves it no place and why, plus a **revision proposal** (what → what · reason · application scope `from new code onward` / `full migration`) — **state alongside the in-contract resolutions you reviewed and the real grounds for the impossibility** (only when both options are visible does the human decide outside the revision frame. The existence of existing violations is no reason for revision — the default handling of a violation is fixing the code, and the decision to lower a rule to fit reality is the human's. If the work could also be read as staying within the contract, confirm with the human — the failure direction goes to a question, not silent deviation) ② once the human approves, add one line to the revision history and then edit the body (history rows are never deleted — after finalization this revision procedure is the only write path to the file) ③ then implement per the new contract. When the application scope is `full migration`, migrating the existing code is not this scope's work — the human intakes it with a separate instruction (development phase (joblist in progress): this skill's migration procedure — `references/architecture-lifecycle.md`; operations phase (after development completes): develojt-code-changer. `from new code onward` coexistence is not rot as long as it is recorded — unrecorded coexistence is the rot). **When the human instructs a structural change itself** (top-down — "change the structure to …", with no mid-implementation encounter) the same revision rules apply (revision proposal → human finalization → history + body), with the survey/report/migration procedures single-truthed in `references/architecture-lifecycle.md`. In a project without a contract this procedure does not exist (structure fully autonomous — as before; establishing a contract itself is mid-project adoption via a human instruction — the adoption procedure in the same document). **Even when the contract seems to have a place for it, if this implementation brings in a new kind of system boundary (a first external-integration kind, a new protocol, a new resident process, a new storage kind), state it in one line in the report** — whether to absorb it under the existing rules or revise a new place into the contract is the human's call (the failure direction goes to a question, not silent absorption — the human checkpoint against structural drift accumulating through legal absorption; the report template's 'Structure signal' line).

## Operations-phase changes — to develojt-code-changer (moved)

Post-development requirement additions/changes/deletions and requirement-invariant code edits (review fixes, refactoring) are received by the **develojt-code-changer skill** — the operations-change front door that auto-enters on a stated change intent. The same applies when old flags (`--review`/`--change`/`--add`) appear in the arguments (the guidance rule in the report & approval gate). What remains in this skill is **new implementation (joblist bundles / EP units) and the PDCA reinforcement within it** only. **Mid-development (unchecked bundles remaining in the joblist) requirement additions/changes are not changer intake either** — carry them into the SPEC and the ledger via deriver incremental/change → spliter incremental, then this skill implements them as the next bundle (exactly the stop-and-report route of 'When a design change is needed').
