# PRD.md Template

Below is the template for the final deliverable, `plan/PRD.md`.
Generate the file by filling this format with the information collected through conversation.

[Required] The section structure (## 1·2·3·4) and view labels (`**[Foundation]**` etc.) must not change — they are the compatibility baseline for validate.py and spec-deriver.
[Required] `{check}` slots take `x` or a space; `{...}` slots take the collected information in natural language.
[Required] Free-form areas (`_(add ... here)_`) stay empty — they are for the human to fill over days. Never fill them automatically.
[Required] Number the epics continuously from 1, from `[Foundation]` through `[Quality]`.
[Required] Write each AI hint line in the `N. [AI] sentence` format (e.g., `1. [AI] A staff member views the list on screen`) — validate.py counts only lines in this format as hints.
[Required] `{user_epics}`/`{user_considerations}` slots: if content was collected during conversation, enter it numbered from 1 and remove the empty scaffold lines below (`1. `–). If none, delete only the placeholder line and leave the empty scaffold as-is.
[Required] Fill Language/Framework/DB/Middleware under Core Technologies with a value or `None` — no blanks (validate.py catches them as FAIL). Fill Model with a value or `None` too — it is outside validate.py's checks, and the STEP 2 procedure guarantees it is filled (the same grammar as the Technology Verification section — an older PRD without a Model row is not a FAIL). `Other` may stay empty.
[Required] The `{tech_verifications}` slot in the Technology Verification section: if researched, enter the table (`| Technology (checked version) | Role | Verified capability | Verdict | Source | Constraints/cautions |`); if the user decided "proceed without research", enter one line, `Not researched (user decision, {date})` — never leave it blank (the record distinguishing a human decision from silent omission; outside validate.py's checks — the STEP 2 technology verification procedure guarantees it gets filled). When the research finalizes a means of implementation (a finalized package/wrapper, a replacement technology, a version constraint), reflect that decision in the Core Technologies fields above as well — what carries over into the SPEC tech stack is the `### Core Technologies` fields (STEP 2 step 4).

### Business Epics [human-written]

> Write the core things this system actually has to do below.
>
> **How to write:**
> - Number them, one per line
> - Use the form "someone does something" or "a Y capability is needed"
> - One or two sentences are enough. No need to write long
> - Use business language rather than technical terms
> - It doesn't have to be perfect. Write whatever comes to mind
> - You can add/edit/delete freely later
> - It's fine to write what the [AI] hints above bring to mind
>
> **Good examples:**
> ```
> 1. A staff member views today's submitted requests on a web screen
> 2. When a request is registered, the approver is notified
> 3. Processing history can be viewed by date/staff member
> 4. If a request stays unprocessed past its deadline, the staff member is notified
> ```
>
> **Examples to avoid:**
> ```
> ❌ "A viewing feature" → too short and vague. Who, what, how?
> ❌ "Implement JWT-based auth" → technical implementation details belong to the SPEC stage
> ❌ "The system should run well" → a truism carrying no information
> ```
